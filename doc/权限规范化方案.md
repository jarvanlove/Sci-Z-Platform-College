# 权限规范化方案（基于 Sa-Token + 现有 RBAC）

## 一、现状分析

### 1.1 已有能力

| 能力 | 说明 |
|------|------|
| **Sa-Token** | 登录、Session、路由鉴权；`StpUtil` 获取当前用户；`CustomStpInterface` 为 Sa-Token 提供「角色码」「权限码」数据源。 |
| **RBAC 表结构** | `sys_role`、`sys_permission`、`sys_role_permission`、`sys_user_role` 已存在；支持按行业（industry_type）隔离。 |
| **权限数据** | `init_permission_data.sql` 已初始化：角色（admin/user）、菜单权限（menu:*）、部分按钮权限（button:declaration:create、button:project:edit 等）。 |
| **PermissionService** | `findRoleCodes(userId, industryType)`、`findPermissionCodes(userId, industryType)`、`buildMenus(...)`；供 CustomStpInterface 与登录接口使用。 |
| **DataPermissionUtil** | 仅做两件事：`isAdmin()`（是否包含 role_code=admin）、`getDataPermissionFilter()`（admin 返回 null，否则返回当前用户 ID）；被多处 Repo/Service 直接调用。 |

### 1.2 当前业务权限实现方式（问题所在）

申报、项目、知识库等业务权限**未使用** `sys_permission` 的权限码，而是：

- **硬编码角色**：各处直接调用 `DataPermissionUtil.isAdmin()`。
- **硬编码业务规则**：在 Service/Repo 中写死「创建人 / 项目负责人(manager_id) / 项目成员 / 知识库 owner / 共享用户」等判断，逻辑分散在：
  - DeclarationServiceImpl、DeclarationRepoImpl
  - ProjectServiceImpl、ProjectRepoImpl、ProjectMemberRepo
  - KnowledgeServiceImpl、KnowledgeFileRelationServiceImpl
  - FileServiceImpl、SysAttachmentRepoImpl 等

带来的问题：

1. **与 RBAC 脱节**：库里已有权限码和角色绑定，业务层几乎不用，只用了“是否 admin”。
2. **难以扩展**：新增角色或规则（如“只读成员”“审批人”）要在多处改代码。
3. **维护成本高**：权限规则变更需要改 N 个 Service/Repo，容易遗漏。
4. **前端与后端语义重复**：前端根据 `canEdit` 等字段显隐按钮，后端又按“创建人/负责人/成员”各写一遍，两处逻辑需长期保持一致。

---

## 二、目标

- **统一入口**：业务层不直接写“是否 admin、是否创建人、是否负责人”，改为调用统一的权限判断服务。
- **可配置**：功能级权限（菜单/按钮）继续用 `sys_permission` + 角色绑定；数据级权限（谁对哪条数据可操作）通过“规则 + 资源归属”集中判断，便于后续改为配置或扩展。
- **少改业务代码**：新增/变更权限时，优先改权限配置或权限服务，而不是改每个业务方法。
- **与现有体系兼容**：不推翻 Sa-Token 与现有 RBAC 表结构，在其上做“规范化使用”和“数据权限抽象”。

---

## 三、权限分层（建议）

| 层级 | 含义 | 当前状态 | 目标 |
|------|------|----------|------|
| **功能权限** | 能否访问某菜单、某按钮（与具体数据无关） | 已有 menu:*、button:* 及角色绑定；部分接口/前端未统一用权限码 | 接口与前端统一按权限码鉴权 |
| **数据权限** | 能否对某条数据（某申报/某项目/某知识库）做查看、编辑、删除等 | 完全硬编码在业务代码中 | 抽象为“资源权限服务”，按资源类型 + 操作 + 资源 ID 返回是否允许 |

说明：

- **功能权限**：继续用 Sa-Token + `sys_permission` 的 permission_code；Controller 可用 `@SaCheckPermission("button:xxx")` 或自定义注解；前端用接口返回的权限列表或菜单树控制显隐。
- **数据权限**：不依赖“某条 permission 记录”，而依赖“资源归属关系”（创建人、负责人、成员、共享人等）。建议单独抽象一层，由“资源权限服务”根据资源类型查库判断，业务层只调用“能否对资源 A 做操作 B”。

---

## 四、规范化改造方案（不写具体代码，只写步骤与约定）

### 4.1 功能权限：补全权限码并统一使用

**（1）在 sys_permission 中补全业务相关权限码**

与现有 `button:*` 风格保持一致，例如（按需增删）：

- 申报：`button:declaration:edit`、`button:declaration:delete`、`button:declaration:submit` 等
- 项目：已有 `button:project:edit`、`button:project:delete`；可补 `button:project:member_manage` 等
- 知识库：`button:knowledge:create`、`button:knowledge:edit`、`button:knowledge:delete`、`button:knowledge:permission` 等

通过迁移脚本插入，并绑定到对应角色（如 admin 全选，user 按需勾选）。

**（2）后端接口**

- 需要“功能级”控制的地方（如：是否允许进入编辑页、是否允许点“删除”）：使用 Sa-Token 的权限校验，例如 `StpUtil.checkPermission("button:project:edit")` 或封装成 `PermissionUtil.hasPermission("button:project:edit")`，避免在业务逻辑里写 `if (isAdmin())`。
- 登录/用户信息接口已返回角色与权限列表，前端可直接使用。

**（3）前端**

- 菜单：继续用现有菜单树（来自权限）。
- 按钮：用权限码控制显隐，例如 `v-if="hasPermission('button:project:edit')"`，或沿用“后端在列表/详情里返回 canEdit/canDelete”的方式；若采用后者，建议在文档中约定“这些字段由数据权限服务计算”，避免前端再写一遍角色/创建人逻辑。

### 4.2 数据权限：抽象“资源权限服务”

**（1）概念**

- **资源类型**：declaration（申报）、project（项目）、knowledge（知识库）等。
- **操作**：view、edit、delete、manage_member 等（可与业务强相关，如 knowledge 的 share）。
- **输入**：当前用户 ID + 资源类型 + 资源 ID（+ 可选上下文，如项目下的知识库）。
- **输出**：boolean 或简单枚举（如 仅查看 / 可编辑）。

**（2）实现思路（建议）**

- 新建或扩展一个 **ResourcePermissionService**（或 **DataPermissionService**），提供诸如：
  - `canView(userId, resourceType, resourceId)`
  - `canEdit(userId, resourceType, resourceId)`
  - `canDelete(userId, resourceType, resourceId)`
- 内部按 resourceType 分支：
  - **declaration**：查申报表 + 关联项目；判断当前用户是否为申报人、或项目创建人/负责人/成员（查 project、project_member、manager_id 等）。
  - **project**：查项目表 + 成员表；判断是否为项目创建人、负责人(manager_id)、或成员。
  - **knowledge**：查知识库表；判断是否为创建人(owner_id)、或（项目知识库）项目负责人/成员；若是个人知识库且 is_shared=1 且当前用户非创建人，则仅 view。
- 将当前散落在各 Service/Repo 的“是否创建人/是否负责人/是否成员”等逻辑，**逐步迁移**到该服务中，形成唯一真相源；业务层只调用 `resourcePermissionService.canEdit(userId, "project", projectId)` 等，不再写 `if (isAdmin() || createdBy.equals(userId) || managerId.equals(userId))`。

**（3）与 DataPermissionUtil 的关系**

- **DataPermissionUtil**：建议保留，但职责收窄为“仅提供当前用户身份与是否 admin”：
  - `getDataPermissionFilter()`：仍可用于“列表数据过滤”（admin 看全部，非 admin 只看自己创建的）这类通用场景。
  - `isAdmin()`：可保留，用于“admin 无视数据权限”的短路判断（在 ResourcePermissionService 内部先判断 isAdmin，再查资源归属）。
- 业务层不再直接根据“是否 admin + 创建人/负责人/成员”写一长串 if，改为调用 ResourcePermissionService。

**（4）列表/详情的“可操作”字段**

- 列表、详情接口中返回的 `canEdit`、`canDelete` 等，**由后端在组装 DTO 时调用 ResourcePermissionService 计算**，保证与真实数据权限一致；前端只根据这些字段显隐按钮，不再依赖前端自己算“是否创建人/负责人”。

### 4.3 改造顺序建议

| 阶段 | 内容 | 说明 |
|------|------|------|
| **1. 文档与权限码** | 梳理现有所有“谁能对谁做什么”的规则，写成文档；在 sys_permission 中补全并绑定权限码 | 为后续改造和测试提供依据；不改变现有行为 |
| **2. 抽象资源权限服务** | 新建 ResourcePermissionService，按资源类型实现 canView/canEdit/canDelete；内部可先复用现有 Repo 查询（申报/项目/成员/知识库） | 先集中逻辑，再逐步替换调用方 |
| **3. 替换业务层判断** | 在 DeclarationServiceImpl、ProjectServiceImpl、KnowledgeServiceImpl、FileServiceImpl 等中，将“是否 admin + 创建人/负责人/成员”替换为调用 ResourcePermissionService | 每次只改一个模块，便于回归 |
| **4. 统一功能权限使用** | Controller 或统一入口处用权限码做功能级校验；前端按钮与权限码或后端返回的 canEdit 等对齐 | 避免新功能继续写 isAdmin |
| **5. 前端收敛** | 前端去掉“根据角色/ownerId 自己算 canEdit”的逻辑，统一依赖后端返回的 canEdit/canDelete 等 | 与 4.2（4）一致 |

### 4.4 后续扩展（可选）

- **角色与数据权限规则**：若未来希望“某角色默认对某类资源可编辑”，可在配置或表中增加“角色-数据权限规则”，由 ResourcePermissionService 在“资源归属”之上再叠一层“角色规则”。
- **审计**：权限判断集中后，便于在 ResourcePermissionService 内打日志或埋点，便于审计“谁在何时对哪条数据做了何种操作”。

---

## 五、实施时注意点

1. **不破坏现有行为**：先做“等价替换”——用 ResourcePermissionService 复刻当前硬编码结果，再逐步优化规则。
2. **异步/多线程**：当前 DataPermissionUtil、LoginUserUtil 已考虑异步线程（AsyncUserContext）；ResourcePermissionService 若需要当前用户，应统一通过 LoginUserUtil/AsyncUserContext 获取，避免再起一套上下文。
3. **性能**：ResourcePermissionService 内可能多次查库（申报+项目+成员等）；可对“当前用户 + 资源类型 + 资源 ID”做短期缓存（如本次请求内缓存），避免同一请求内重复计算。
4. **行业**：现有权限按 industry_type 隔离；数据权限若也按行业（如只查本行业项目），需在 ResourcePermissionService 中带入行业参数或从当前用户上下文取行业。

---

## 六、小结

| 项目 | 建议 |
|------|------|
| **功能权限** | 继续用 Sa-Token + sys_permission；补全申报/项目/知识库相关 button 权限码；接口与前端统一用权限码或后端返回的可见性字段，避免到处写 isAdmin。 |
| **数据权限** | 抽象 ResourcePermissionService（或 DataPermissionService），按资源类型 + 操作判断“当前用户对某条数据是否可操作”；业务层只调该服务，不再写“isAdmin 或创建人或负责人或成员”的长串 if。 |
| **DataPermissionUtil** | 保留，职责收窄为“是否 admin + 数据过滤用 userId”；具体“谁能改这条数据”交给 ResourcePermissionService。 |
| **改造顺序** | 先文档化 + 补权限码 → 再实现资源权限服务并逐步替换业务层判断 → 再统一功能权限使用与前端显隐逻辑。 |

按上述方式改造后，权限规则集中、可配置性提高，后续业务扩展或权限变更时，主要改权限表配置和 ResourcePermissionService，避免在大量业务代码中硬编码。
