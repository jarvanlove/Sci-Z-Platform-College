## 一、需求总览

| 维度 | 现状 | 目标 |
|------|------|------|
| **匹配团队** | 仅关键词模糊 SQL（LIKE），无匹配时无结果 | 支持「相似」匹配：无/少 SQL 结果时用 AI/语义/向量 等技术召回相似团队 |
| **团队明细** | 仅基础信息：成员列表、关联项目，效率/荣誉占位 | 支持点进**每个项目**看明细：负责人介绍、成员介绍、效率/荣誉等指标用**图表**展示；前端改版 |
| **分发** | 领导选申报 ID + 目标团队，直接创建项目并复制成员 | 改为**消息驱动**：领导选「匹配提示词」+ 目标团队 → 给**项目负责人**发消息；负责人**接受/拒绝**；接受则后台自动创建申报+项目+项目知识库；拒绝则填原因，领导收推送 |
| **消息** | 未开发 | 站内消息表与 API、前端消息中心、推送接收（含分发相关通知） |

整体业务流：**领导输入科研主题 → 系统匹配（含相似）→ 查看项目明细（含图表）→ 选择分发给某团队（项目负责人）→ 负责人收消息并接受/拒绝 → 接受则自动生成申报、项目、项目知识库；全程消息闭环。**

## 二、匹配团队：相似匹配（AI/语义）

### 2.1 问题

- 当前：`DeclarationRepo.findIdsByKeywordForMatch` + `ProjectRepo.findForIndustryEducationMatch` 均为 **LIKE %keyword%**，用户输入 keyword 若无命中则结果为空。
- 领导期望：**语义相近**的团队也能被召回（例如输入「人工智能」能匹配到「机器学习」「深度学习」相关项目）。

### 2.2 方案要点

1. **保留现有逻辑**：先按 keyword 做一次模糊 SQL 匹配，若有结果则按现有时序/数据权限返回。
2. **相似匹配扩展**（当 SQL 结果数 &lt; 阈值，如 0 或 &lt; limit 时）：
   - **方案 A（推荐）**：调用现有或新增 **AI 能力**（摘要/embedding）对 `research_topic`、`research_direction`、`content_summary`、项目 `name`/`description` 做语义表征，用 keyword 的向量做相似度检索（向量库或 DB 向量列），取 Top N 补足结果。
   - **方案 B**：用 AI 根据 keyword 生成若干「同义/近义关键词」，再对生成词做多轮 LIKE 或 IN 查询合并去重。
3. **接口**：仍使用 `POST /api/industry-education/teams/match`，请求体可增加可选参数，例如：
   - `useSemanticMatch: boolean`（默认 true）：当模糊匹配不足时是否启用相似匹配；
   - `limit` 含义不变。
4. **响应**：可在 `TeamMatchResp` 中增加可选字段，如 `matchType: "keyword" | "semantic"`、`score`，便于前端区分展示（如标注「语义匹配」）。

### 2.3 后端改造点

- 在 `IndustryEducationServiceImpl.matchTeams` 中：
  - 若 `declarationIds` 为空或 `projects.size() < limit` 且 `useSemanticMatch == true`，调用「相似匹配」服务（新模块，如 `TeamSemanticMatchService`），传入 keyword、limit、数据权限上下文；
  - 合并/去重、排序后截断为 limit 条返回。
- 相似匹配需遵守**数据权限**：只对当前用户可见的申报/项目做语义检索。

## 三、团队明细：项目级明细与图表

### 3.1 需求

- 领导需要的不只是「当前团队（一个项目）的基础信息」，而是：
  - **成员列表** + **每个成员的介绍**（如简介、职称、专长）；
  - **关联项目列表**中，能**点进每个项目**看该项目的：
    - 项目负责人介绍；
    - 项目成员及各自介绍；
    - **效率、荣誉**等指标，用**不同图表**展示（如折线图、柱状图、荣誉列表等）。

### 3.2 接口扩展

- **团队明细主接口**：`GET /api/industry-education/teams/{id}` 增强返回：
  - 负责人介绍（如 `leaderIntro`，来自用户扩展信息或固定简介字段）；
  - 成员列表项增加 `intro`（成员介绍）；
  - 关联项目列表项增加：负责人姓名、负责人介绍、成员数、状态、以及**项目维度**的效率/荣誉汇总（若暂无真实数据可先占位，结构预留）。
- **项目级明细**（新接口）：`GET /api/industry-education/projects/{projectId}/detail`  
  - 返回：项目名称、状态、负责人姓名+介绍、成员列表（含介绍）、效率指标（结构化，便于前端作图）、荣誉列表（结构化）。
  - 便于前端在「团队明细」中点击某项目后，拉取该项目详情并展示图表。

### 3.3 数据结构建议（项目明细）

- **效率指标**：如 `{ completionRate, avgCycleDays, milestoneCount, ... }`，前端可映射为折线图（时间维度）、柱状图（项目间/成员间对比）等。
- **荣誉**：如 `[{ title, level, date }]`，前端可表格或时间线展示。
- 若当前库表无「介绍」「效率」「荣誉」字段，需在用户表扩展或新增「项目/成员扩展信息」表，或先占位返回固定结构，后续再接真实数据。

### 3.4 前端改版要点

- **团队明细**：由单层「成员+项目列表+占位」改为：
  - 顶部：团队名称、负责人、负责人介绍；
  - 成员列表：头像/姓名/角色 + 介绍（可折叠）；
  - 关联项目：卡片列表，每项可点击「查看项目明细」；
- **项目明细**（抽屉或子页）：
  - 项目名、状态、负责人介绍、成员介绍；
  - **图表区**：效率（折线/柱状）、荣誉（表格或时间线）；
  - 与产教研流程衔接：可提供「分发给该团队」入口（即分发给该项目负责人）。

## 四、分发：消息驱动与接受/拒绝

### 4.1 流程重设计

- **领导侧**：
  - 在匹配结果中查看团队/项目明细后，选择「分发给该团队」；
  - 分发时**不再选择申报 ID**，而是以**当前匹配的提示词（领导输入的科研主题/关键词）** 作为「待办科研项目」描述；
  - 点击分发 = 向该团队对应的**项目负责人**发送一条**站内消息**，内容包含：
    - 分发人：XXX（当前登录领导）；
    - 科研项目描述：XXX（即领导输入的匹配关键词/提示词）；
    - 业务类型：产教研分发（便于前端跳转与后端处理接受/拒绝）。

- **被分发人（项目负责人）侧**：
  - 登录后收到**推送消息**；
  - 打开消息：展示「谁」「将哪个科研项目」分发给您；
  - 操作：**接受** / **拒绝**。

- **接受**：
  - 后端自动创建：**申报**（研究课题 = 领导输入的提示词，负责人 = 当前用户）、**申报项目**、**项目知识库**（与现有「申报通过后创建项目+知识库」逻辑一致或复用）；
  - 领导收到一条推送：「XXX 已接受科研项目 XXX」。

- **拒绝**：
  - 被分发人填写**拒绝原因**；
  - 领导收到推送：「XXX 拒绝了科研项目 XXX，原因：…」。

### 4.2 接口设计

- **分发动作（领导）**：由「指定 declarationId + targetTeamId」改为「指定匹配描述 + 目标团队」。
  - 新请求体示例：`{ topicLabel: string, targetTeamId: long }`（`topicLabel` = 领导输入的匹配关键词/提示词）；
  - 接口：`POST /api/industry-education/assign` 或新路径 `POST /api/industry-education/distribute`；
  - 逻辑：校验 targetTeamId（项目）存在且取负责人 → 创建一条「产教研分发」类型站内消息，接收人 = 项目负责人，消息体含 topicLabel、分发人、targetTeamId（用于接受时确定负责人与团队上下文）。

- **接受（被分发人）**：`POST /api/industry-education/distribute/{messageId}/accept`
  - 校验：当前用户为消息接收人、消息状态为待处理；
  - 在事务内：创建申报（research_topic = topicLabel，负责人 = 当前用户）、创建项目、创建项目知识库（复用现有 Knowledge 创建逻辑）；
  - 更新消息状态为已接受，并给**分发人**发一条「XXX 已接受 XXX」的站内消息。

- **拒绝（被分发人）**：`POST /api/industry-education/distribute/{messageId}/reject`
  - 请求体：`{ reason: string }`；
  - 校验：当前用户为消息接收人、消息状态为待处理；
  - 更新消息状态为已拒绝，写入拒绝原因；给**分发人**发一条「XXX 拒绝了 XXX，原因：…」的站内消息。

### 4.3 数据与权限

- 系统以**项目**为导向，团队可能仅有项目负责人一人；分发对象即该项目的 `manager_id`（项目负责人）。
- 消息表需包含：类型（产教研分发）、发送人、接收人、主题/描述、关联业务 ID（如 targetTeamId）、状态（待处理/已接受/已拒绝）、拒绝原因、时间等。

## 五、站内消息与推送

### 5.1 能力范围

- **站内消息**：列表（分页）、未读数量、单条已读、全部已读、删除（可选）；
- **推送**：前端能**实时或准实时**收到新消息（WebSocket、SSE 或短轮询），用于「新消息」角标、消息中心红点、以及分发接受/拒绝结果通知领导。

### 5.2 后端

- **消息表**：`sys_message`（已建表，见第八节）；字段含 id, type, sender_id, receiver_id, title, content, extra_json, status, read_time 等。
- **消息 API**（已实现）：  
  - `GET /api/messages`：分页列表，支持未读筛选（query: page, size, unreadOnly）；  
  - `GET /api/messages/unread-count`：未读数；  
  - `GET /api/messages/{id}`：消息详情；  
  - `PUT /api/messages/{id}/read`：标已读；  
  - `PUT /api/messages/read-all`：全部已读。  
- **消息推送**：采用 **WebSocket**。  
  - 端点：`/ws/message`，连接时 query 携带 `token=xxx`（Sa-Token 的 token），服务端校验后将当前会话与 userId 绑定。  
  - 当创建新消息时（如分发、接受/拒绝结果通知），向对应用户的在线 WebSocket 连接推送 JSON：`{ "type": "NEW_MESSAGE", "messageId", "title", "messageType" }`，前端据此更新未读数或拉取列表。

### 5.3 前端

- **消息中心**：布局内常驻入口（如顶部导航铃铛）+ 消息列表页；列表项可区分类型（如产教研分发、系统通知）；点击进入详情，产教研分发类展示「接受/拒绝」按钮（仅接收人且待处理时）。
- **实时接收**：建立 WebSocket/SSE 连接，收到新消息时更新未读数、可弹出轻提示或刷新列表。

### 5.4 系统消息菜单位置

- **入口**：用户下拉菜单中增加「系统消息」菜单项，位置在**操作手册**下方、**系统设置**（及分隔线）上方。
- **前端**：侧边栏用户下拉（ToCSidebar）中顺序为：个人信息 → 安全设置 → 操作手册 → **系统消息** → （分隔线）系统设置 → 切换主题 → （分隔线）退出登录。点击「系统消息」跳转至 `/user/messages`（系统消息/站内消息列表页）。

## 六、UI/UX 场景与页面设计

遵循项目内 **ui-ux-pro-max** 规范：可访问性（对比度、焦点、aria）、触控目标 ≥44px、加载与错误反馈、Vue + Element Plus 一致性。

### 6.1 场景一：匹配与列表（领导）

- **页面**：产教研主页面（当前 `IndustryEducation.vue` 增强）。
- **布局**：顶部标题与说明 → 申报课题输入区（textarea，0/500 字）→「匹配团队」按钮 → 结果区。
- **结果区**：团队卡片网格（保留现有），每卡展示团队名、负责人、成员数、完成数、效率占位；若有 `matchType === 'semantic'` 可显示标签「语义匹配」。
- **操作**：每卡「查看明细」「分发给该团队」；点击卡片或「查看明细」打开团队明细抽屉。

### 6.2 场景二：团队明细与项目明细（领导）

- **团队明细抽屉**：右侧抽屉，标题「团队明细」。内容：负责人+介绍、成员列表（姓名、角色、介绍）、关联项目列表（每项可点击「查看项目明细」）、底部「分发给该团队」。
- **项目明细**：抽屉内再打开一层或新抽屉/弹窗。内容：项目名、状态、负责人介绍、成员介绍、**效率图表**（如折线/柱状）、**荣誉**（表格或时间线）；底部可带「分发给该团队」。
- **图表**：使用 ECharts 或项目现有图表库；类型与 ui-ux-pro-max 中 chart 规范一致（按数据类型选折线/柱状等），保证可访问性与颜色对比度。

### 6.3 场景三：分发操作（领导）

- **入口**：在团队卡片或团队/项目明细中点击「分发给该团队」。
- **弹窗**：标题「分发科研项目」。展示当前选中的团队/项目及负责人；**不再输入申报 ID**，展示将使用的「科研项目描述」为当前匹配关键词（可只读或允许领导微调）。确认后调用分发接口，发送站内消息给负责人；成功提示并关闭抽屉/弹窗。

### 6.4 场景四：消息中心与接受/拒绝（被分发人）

- **消息列表**：铃铛或「消息」入口 → 消息列表页；列表项显示标题、摘要、时间、未读标识；类型为「产教研分发」的项可点击进入详情。
- **消息详情**：展示「XXX 将以下科研项目分发给您：XXX」；若当前用户为接收人且状态为待处理，显示**接受**、**拒绝**按钮（触控目标 ≥44px）。
- **拒绝**：点击拒绝后弹出输入框填写原因，提交后领导收到推送；接受则直接提交，后台创建申报+项目+知识库，领导收到「已接受」推送。

### 6.5 设计系统建议（ui-ux-pro-max）

- **产品类型**：管理后台 / 科研管理 Dashboard。
- **风格**：简洁、专业，与现有申报/项目/仪表板一致；卡片、表格、图表与 Element Plus 组件统一。
- **图表**：效率用折线或柱状；荣誉用表格或时间线；配色符合无障碍对比度。
- **交互**：加载态（骨架或 loading）、错误态（表单下或顶部提示）、成功态（Message 或轻提示）；键盘可聚焦、焦点可见。

## 七、实现顺序与技能参考

### 7.1 建议实现顺序

1. **站内消息基础**：消息表、CRUD API、未读数、前端消息中心入口与列表页。
2. **推送**：WebSocket 或 SSE 推送新消息，前端接收入口与未读更新。
3. **分发流程改造**：领导侧改为「topicLabel + targetTeamId」发消息；被分发人消息详情页「接受/拒绝」；接受时创建申报+项目+知识库；拒绝时写原因并通知领导。
