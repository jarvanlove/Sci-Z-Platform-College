## 1. 目标与范围

### 1.1 目标

- **AI 能回答「系统中任何问题」**：用户可在 AI 对话中提出**任何与当前平台相关**的问题——不只使用说明与 FAQ，还包括**项目问题、系统中已有的功能、以及功能所包含的数据**（如我的项目、待办、申报、统计等），AI 都基于可靠信息（文档 + 实时数据）作答并反馈给用户。
- **越用越聪明**：随系统用户与数据增多，通过「系统知识库内容迭代 + 使用反馈闭环 + 实时数据注入」，用户提问得到的答案越来越精确、覆盖越来越全。
- **保持现有设计**：继续以 Dify 为 AI 对话与知识库底座，不替换为其他大模型或 RAG 架构。

### 1.2 「系统中任何问题」范围（均需可问、可答）

| 类型 | 说明 | 示例问题 | 数据来源 |
|------|------|----------|----------|
| 功能与操作 | 系统有哪些功能、怎么用 | 「如何创建项目？」「申报流程在哪？」「知识库怎么上传文件？」 | 产品文档、操作说明、FAQ（系统知识库） |
| 平台规则与约定 | 业务规则、权限、约定 | 「项目截止日期能改吗？」「谁可以审批？」「哪些人能看到我的知识库？」 | 业务规则、权限说明（系统知识库） |
| 功能包含的数据（与我相关） | 功能模块里的业务数据 | 「我有哪些项目？」「我的待办有几条？」「我负责的申报有哪些？」 | 实时业务数据（需工具/API） |
| 功能包含的数据（统计与概览） | 平台级统计、报表 | 「当前有多少用户？」「本月新增多少项目？」「各状态项目数量？」 | 统计/报表（需工具/API 或预生成） |

前两类由**系统知识库**承载；后两类由**我们侧提供只读 API**，经 Dify 工具节点调用后注入回答。**最终效果**即：用户问「系统里的功能 + 功能里的数据」任何问题，都能得到基于真实信息的反馈，并随使用与数据增长**越用越聪明**。

## 2. 最终效果（方案三目标）

本方案所要达到的**最终效果**如下，需通过方案一、二、三分阶段实施后整体达成：

- **用户可在 AI 对话中询问关于系统的任何问题**  
  - 不只「系统怎么用」类问题，还包括：**项目相关**（我的项目、项目状态、申报进度）、**系统中有的功能**（有哪些模块、各自做什么）、**功能包含的数据**（待办、审批、统计、用户与权限等）。  
  - 上述问题都能得到**基于真实信息**的反馈：来自系统知识库的文档与 FAQ，以及来自我们后端 API 的实时业务数据。

- **越用越聪明**  
  - 系统知识库随使用反馈持续补充与修正，文档与 FAQ 覆盖更全、表述更准。  
  - 实时数据接口返回的数据量随业务增长（用户增多、项目/申报/待办变多），答案更丰富、更精确。  
  - 通过日志与反馈统计，不断发现未覆盖或答得不好的问题，反哺知识库与工具设计，形成闭环。

- **保持目前设计**  
  - 仍以 Dify 为对话与知识库引擎；我们侧只增加「系统知识库」与「只读工具 API」，不替换现有架构。

## 3. 现状与约束

- **对话与检索**：已有 Dify Chatbot + 多知识库（用户可选 `knowledgeIds`），会话内多轮、conversation_id 已打通。
- **知识库**：我们创建/管理知识库，文档同步到 Dify 数据集；检索与索引由 Dify 完成。
- **约束**：不改变「Dify 作为对话与知识库引擎」的定位；尽量复用现有 Chatbot、知识库、会话模型。

---

## 4. 整体思路

- **统一入口**：仍用现有 AI 对话入口；通过「是否带系统知识库」「是否带实时数据能力」区分能力，不另做一套对话产品。
- **系统知识库**：在 Dify 中维护一个**仅平台使用的「系统知识库」**（一个 Dataset），内容为：产品说明、操作指南、FAQ、业务规则、功能概览等。该库作为检索源之一参与回答，使 AI 能答「功能与规则」类问题。
- **实时数据（方案三）**：我们提供只读 HTTP API（按业务模块：项目、申报、待办、统计等），Dify 通过工具节点调用，将结果注入回答，使 AI 能答「功能包含的数据」类问题。
- **越用越聪明**：
  - **短期**：系统知识库内容越全、质量越高，回答越准。
  - **中期**：**使用反馈与内容迭代**（方案二）——收集高频/未覆盖/负反馈问题，反哺系统知识库，答案更精确、覆盖更全。
  - **长期**：**实时数据 + 反馈**（方案三 + 方案二）——数据量增大使答案更丰富；日志与反馈用于优化工具与提示词，形成闭环。

下面分三个方案：方案一（仅系统知识库）、方案二（+ 反馈与迭代）、方案三（+ 实时数据）；**方案三为必须达成的最终效果**，一、二为其基础。

---

## 5. 方案一：仅系统知识库（最小改动）

### 5.1 思路

- 在 Dify 中创建一个**系统专属知识库**（如「Sci-Z 平台使用说明与 FAQ」），不面向普通用户直接编辑，仅由运营/管理员维护。
- 对话时：在现有「用户所选知识库」基础上，**始终附加该系统知识库**（或提供「问系统」模式仅用系统知识库），这样用户问系统相关问题即可被检索到并作答。
- 不新增 Dify 工作流、不接我们后端 API；完全在现有「Chatbot + 多知识库」能力内完成。

### 5.2 要做的事

| 序号 | 事项 | 说明 |
|------|------|------|
| 1 | 在 Dify 创建「系统知识库」 | 使用与现有知识库相同的索引/检索策略（建议与图2 一致：高质量、权重融合、top_k 等），便于统一体验。 |
| 2 | 在我们库中登记该系统知识库 | 在 `sys_knowledge_base`（或等价）中占一条记录，标记为「系统知识库」（如 `kb_type=SYSTEM` 或 `owner_id=system`），并保存其 Dify dataset_id。 |
| 3 | 对话时附带系统知识库 | 调用 Chatbot 前，在 `updateChatbotKnowledgeBases` 时，**始终在知识库列表中加入该系统知识库的 Dify ID**（可放首位或末位，视产品偏好）；若用户已选多个知识库，则「系统 + 用户所选」一起参与检索。 |
| 4 | 准备并灌入初始内容 | 将现有产品文档、操作说明、FAQ（Markdown/Word 等）整理后，通过我们已有「上传到知识库」或 Dify API 写入该系统知识库，保证首版即可回答常见系统问题。 |

### 5.3 配置与代码要点

- **配置**：在 `application*.yml` 中增加一项，如 `dify.system-knowledge-base.dify-dataset-id`，指向 Dify 中该系统知识库的 ID；若希望用我们库内记录解析，也可用 `dify.system-knowledge-base.knowledge-base-id`（我们库主键），再在代码中查 Dify ID。
- **代码**：在 `ChatServiceImpl.runWorkflow`（或统一组 knowledgeIds 的地方）中，在传入的 `knowledgeIdList` 前/后**追加系统知识库 ID**（若前端未传「仅问知识库」则追加），再执行现有 `updateChatbotKnowledgeBases(userId, knowledgeIdList, enableSearch)`。

### 5.4 效果与局限

- **效果**：用户任意对话中都可问到「如何用系统、规则是什么、常见问题」等，答案来自系统知识库，与现有 Dify 设计一致。
- **越用越聪明**：仅能通过**人工/半自动扩充系统知识库内容**（更多 FAQ、更细文档）来提升，暂无自动从使用中学习的闭环。
- **局限**：无法回答「我当前有多少项目」「我的待办」等依赖实时数据的问题；这类需方案三。

## 6. 方案二：系统知识库 + 使用反馈与内容迭代

### 6.1 思路

在方案一基础上，增加「从使用中发现问题 → 反哺系统知识库」的闭环，使系统知识库随使用越来越准、覆盖越来越全，为**越用越聪明**提供内容侧闭环。

### 6.2 要做的事

| 序号 | 事项 | 说明 |
|------|------|------|
| 1 | 完成方案一 | 先具备系统知识库并参与检索。 |
| 2 | 记录「问题–检索–回答」日志 | 在对话请求中或流式结束后，落库记录：`user_id`、`conversation_id`、`query`、命中的知识库/文档片段 ID（若 Dify 有返回）、`answer` 摘要或长度、时间。可选：用户点赞/点踩或「是否有用」反馈。 |
| 3 | 统计与挖掘 | 定期（如每周）统计：高频问题、从未命中系统知识库的问题、用户反馈差的问题；可做成简单报表或看板，供运营/产品查看。 |
| 4 | 内容迭代流程 | 运营根据统计结果：新增 FAQ、补充操作说明、修正错误文档；通过我们平台或 Dify 控制台上传/更新到系统知识库，并可选做「文档切分与标题」优化，便于检索更准。 |
| 5 | 可选：半自动建议 | 对「高频且无命中」或「负反馈」问题，用脚本或后台任务生成「建议新增 FAQ」列表（仅建议，由人工审核后写入系统知识库）。 |

### 6.3 数据模型建议

- **表**：如 `ai_system_qa_log`（或类似命名），字段建议：`id`、`user_id`、`conversation_id`、`query`、`retrieved_dataset_ids`（JSON 或文本）、`retrieved_doc_ids`（若有）、`answer_preview`（前 500 字或摘要）、`feedback`（好评/差评/未反馈）、`created_at`。不落库完整 answer 以控制存储与合规。
- **权限**：仅后台/运营可查；可做脱敏或聚合后再展示。

### 6.4 效果

- 系统知识库内容随真实使用持续优化，**答案会越用越聪明、覆盖越全**，且仍完全在现有「Dify + 知识库」设计内。

## 7. 方案三：系统知识库 + 实时数据（工具/API）

### 7.1 思路

若希望 AI 能答「我有哪些项目」「本月申报了多少」等依赖**实时业务数据**的问题，需要在回答时注入我们系统的数据。两种常见做法：

- **A. Dify 工作流 + 工具节点**：我们提供 HTTP API（如「当前用户项目列表」「当前用户待办数量」），Dify 工作流中通过「工具」节点调用这些 API，将结果写入变量并参与生成回答。此时对话需走**工作流**而非仅 Chatbot；或 Chatbot 所在应用配置了工具并能在对话中触发。
- **B. 我们侧预生成「用户/统计摘要」文档并入库**：定时任务（如每日）为每个用户生成一段「您的项目与待办摘要」文本，写入该用户可见的某知识库或系统知识库的「用户专属」文档（需考虑多租户与权限）；检索时命中这些文档即可答「我的项目」类问题。优点是不改 Dify 为工作流，缺点是非实时、且文档膨胀需管控。

推荐优先用 **A（工具调用）** 做「与我相关」的实时问答；B 可作为补充（如离线报表摘要）。

### 7.2 要做的事（以工具调用为例）

| 序号 | 事项 | 说明 |
|------|------|------|
| 1 | 定义我们侧 API | 提供若干只读、幂等的 HTTP 接口，如：`GET /api/ai/tools/my-projects`（返回当前用户项目列表）、`GET /api/ai/tools/my-pending-tasks` 等；需鉴权（如 Sa-Token），仅返回当前用户数据。 |
| 2 | 在 Dify 中配置工具 | 在 Dify 应用（Chatbot 或工作流）中配置「自定义工具」，填写上述 API 的 URL、方法、参数说明；Dify 在需要时请求我们，我们把结果返回给 Dify。 |
| 3 | 对话路由 | 若当前对话是「仅知识库」则仍用现有 Chatbot + 多知识库；若希望支持「问我的数据」，则需该对话走带工具的工作流，或使用已配置工具的 Chatbot（若 Dify 版本支持）。 |
| 4 | 文档与安全 | 在系统知识库中增加简短说明，如「您可以问：我有哪些项目、我的待办」等，并做好 API 鉴权与限流。 |

### 7.3 效果与注意点

- **效果**：AI 可结合实时数据回答「我的项目、我的待办、平台统计」等，答案更精确、更个性化。
- **越用越聪明**：数据量变大（项目变多、待办变多）后，API 返回更丰富，答案自然更精确；若再配合方案二的日志与反馈，可优化「何时该调哪个工具、如何总结返回结果」的提示词或工作流。
- **注意**：需要 Dify 支持 Chatbot 带工具或改用工作流；需评估 Dify 版本与配置方式。

## 8. 推荐实施路径

要达到**最终效果**（用户可问系统中任何问题——功能 + 数据——并越用越聪明），需**按阶段完成方案一、二、三**，其中方案三为必须落地的最后一环。

- **Phase 1（必选）**：落地**方案一**  
  - 创建并登记系统知识库，对话时固定附带该系统知识库，灌入首版文档与 FAQ。  
  - 实现成本低，立刻具备「AI 可答功能与规则类问题」的能力。

- **Phase 2（强烈建议）**：落地**方案二**  
  - 记录问题/检索/反馈日志，建立统计与内容迭代流程，使系统知识库**越用越聪明**（覆盖更全、表述更准）。  
  - 不改变现有 Dify 对话与知识库架构，仅增加我们侧日志与运营流程。

- **Phase 3（必选，最终效果）**：落地**方案三**  
  - 为我们侧提供只读 API（按业务模块：项目、申报、待办、统计等），并在 Dify 中配置工具或工作流，使 AI 能答「功能包含的数据」类问题。  
  - 与方案二结合：对「未命中知识库但适合用工具回答」的问题做统计，用于优化工具与提示词；随用户与数据增多，答案更精确、更丰富。

## 9. 附录：数据与接口清单

### 9.1 方案一/二 涉及配置

- `dify.system-knowledge-base.dify-dataset-id`：Dify 系统知识库的 dataset_id（必填）。  
- 或 `dify.system-knowledge-base.knowledge-base-id`：我们库中系统知识库主键，由代码解析出 Dify ID。

### 9.2 方案二 日志表建议字段

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| user_id | bigint | 用户ID |
| conversation_id | bigint/varchar | 会话ID |
| query | text | 用户问题 |
| retrieved_dataset_ids | varchar/json | 命中的知识库 ID 列表 |
| answer_preview | varchar(500) | 回答摘要（可选） |
| feedback | tinyint | 1 好评 0 差评 null 未反馈 |
| created_at | datetime | 创建时间 |

### 9.3 方案三 我们侧工具 API 清单（需鉴权）

以下按**系统中已有的功能与功能包含的数据**划分，供 Dify 工具节点调用；接口均只读、幂等，鉴权后仅返回当前用户或有权限的数据。返回格式与 Dify 工具节点约定一致（如 JSON 数组或 Dify 文档要求的 schema）。

| 业务模块 | 接口示例 | 说明 |
|----------|----------|------|
| 项目 | `GET /api/ai/tools/my-projects` | 当前用户参与/负责的项目列表（id、name、status、日期等） |
| 项目 | `GET /api/ai/tools/project-stats` | 平台项目统计（总数、按状态分布等，可按权限过滤） |
| 申报/待办 | `GET /api/ai/tools/my-pending-tasks` | 当前用户待办条数或列表 |
| 申报/待办 | `GET /api/ai/tools/my-declarations` | 当前用户申报列表或进度 |
| 知识库 | `GET /api/ai/tools/my-knowledge-bases` | 当前用户可见的知识库列表及简要信息 |
| 用户与权限 | `GET /api/ai/tools/my-profile` | 当前用户基本信息（姓名、角色等，脱敏） |
| 统计概览 | `GET /api/ai/tools/platform-stats` | 平台级统计（用户数、项目数、申报数等，仅管理员或聚合脱敏） |

实际开发时按业务模块逐步增加；每类「功能包含的数据」对应一个或若干工具 API，即可支撑用户问「我有哪些项目、我的待办、平台有多少项目」等，并随数据增多**越用越聪明**。

---

以上方案在**保持现有 Dify 对话与知识库设计**的前提下，通过「系统知识库 + 反馈迭代 + 实时工具 API」实现：**用户可在 AI 对话中询问系统中任何问题（功能 + 数据），并基于这些问题反馈给用户，最终达到越用越聪明**。需按阶段实施：先方案一、再方案二、最后方案三，三者均落地后达成完整效果。
