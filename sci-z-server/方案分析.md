### 1.1 核心线程池架构 (Infrastructure Layer)

项目采用基于 Spring Boot 的异步任务配置，区分 **事件驱动** 与 **全局通用** 两个独立的线程池，符合资源隔离原则。

#### 1.1.1 事件处理线程池 (`eventTaskExecutor`)

**定位**: 领域事件监听 (`@EventListener`) 专用，处理高频、低延迟的内部解耦事件。
**源码位置**: `com.sciz.server.infrastructure.config.event.AsyncEventConfig`

```java
@Bean("eventTaskExecutor")
public Executor eventTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    // 核心线程 5: 应对常态化的轻量级事件
    executor.setCorePoolSize(5);
    // 最大线程 20: 应对突发事件流量
    executor.setMaxPoolSize(20);
    // 队列 100: 适当缓冲，避免 OOM
    executor.setQueueCapacity(100);
    executor.setThreadNamePrefix("event-handler-");
    // 拒绝策略: CallerRunsPolicy - 任务不丢失，回退到主线程执行，形成背压
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(60);
    executor.initialize();
    return executor;
}
```

#### 1.1.2 全局通用线程池 (`globalTaskExecutor`)

**定位**: 处理文件上传、批量数据处理等耗时 I/O 密集型任务。
**源码位置**: `com.sciz.server.infrastructure.config.event.AsyncGlobalConfig`

```java
@Bean("globalTaskExecutor")
public Executor globalTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    // 核心 8: 适配服务器 CPU 核心数 (通常为 2*CPU 或 CPU+1)
    executor.setCorePoolSize(8);
    // 最大 32: 允许较高的并发 I/O
    executor.setMaxPoolSize(32);
    // 队列 200: 较大的缓冲队列
    executor.setQueueCapacity(200);
    executor.setThreadNamePrefix("global-exec-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(60);
    executor.initialize();
    return executor;
}
```

### 2.1 核心重构与 Java 21 现代化改造

#### 2.1.1 移除 `new Thread()` 采用 CompletableFuture ✅ **已实现**

**重构目标**: 消除所有显式线程创建，使用 Spring 管理的 `Executor`，并结合 Java 8+ `CompletableFuture` 实现可编排的异步逻辑。

**实现内容**:

1.  **Service 注入 Executor** ✅:

    - `KnowledgeServiceImpl` 和 `ChatServiceImpl` 已注入 `globalTaskExecutor`
    - 使用 `@Autowired` + `@Qualifier("globalTaskExecutor")` 方式注入

2.  **代码改造 (Refactoring)** ✅:
    已将 4 处 `new Thread(() -> { ... }).start()` 替换为：

    ```java
    // 改造后: Java 21 CompletableFuture
    CompletableFuture.runAsync(() -> {
        try {
            difyApiService.sendChatbotMessageStream(difyRequest, line -> {
                sseStreamHandler.handleStreamLine(emitter, line);
            });
            sseStreamHandler.completeStream(emitter);
        } catch (Exception e) {
            sseStreamHandler.sendErrorAndComplete(emitter, e.getMessage());
        }
    }, globalTaskExecutor); // <-- 指定线程池
    ```

    **实现位置**:

    - ✅ `KnowledgeServiceImpl.chatbotStream()` (Line ~651)
    - ✅ `ChatServiceImpl.handleWorkflowWithKnowledge()` (Line ~125)
    - ✅ `ChatServiceImpl.handleWorkflowWithFileKey()` (Line ~199)
    - ✅ `ChatServiceImpl.callChatbotDirectly()` (Line ~529)

    **收益**:

    - **资源可控**: 线程数受全局线程池限制，防止资源耗尽。
    - **非阻塞**: 提交任务立即返回，不阻塞 Tomcat 线程。
    - **可观测性**: 线程名称规范，便于 Prometheus/Grafana 监控。

#### 2.1.2 引入 Virtual Threads (JDK 21 展望)

鉴于项目已升级至 Java 21，对于 SSE 这类 **I/O 密集型且长时间持有连接** 的任务，这也是 **虚拟线程 (Virtual Threads)** 的最佳应用场景。

**优化建议**:
如果 `globalTaskExecutor` 的平台线程（Platform Thread）资源紧张，可以定义一个专用的虚拟线程执行器：

```java
// Infrastructure Config
@Bean("virtualThreadExecutor")
public Executor virtualThreadExecutor() {
    // Java 21: 为每个任务创建一个轻量级虚拟线程
    return Executors.newVirtualThreadPerTaskExecutor();
}
```

**应用**: 在 `chatbotStream` 中使用 `@Qualifier("virtualThreadExecutor")`。这将允许成千上万个并发 SSE 连接而不会消耗大量的 OS 线程。

```java
// 在 SseStreamHandler 中添加心跳机制
private final ScheduledExecutorService heartbeatScheduler =
    Executors.newSingleThreadScheduledExecutor(r -> {
        Thread t = new Thread(r, "sse-heartbeat");
        t.setDaemon(true);
        return t;
    });

public void startHeartbeat(SseEmitter emitter, int intervalSeconds) {
    heartbeatScheduler.scheduleAtFixedRate(() -> {
        try {
            emitter.send(SseEmitter.event().comment("ping"));
        } catch (IOException e) {
            // 连接已断开，取消心跳
            log.debug("SSE 连接已断开，停止心跳");
        }
    }, intervalSeconds, intervalSeconds, TimeUnit.SECONDS);
}
```

- 在创建 `SseEmitter` 后调用 `sseStreamHandler.startHeartbeat(emitter, sseProperties.getHeartbeatInterval())`

2. **缓存配置说明** ✅:
   - Redis 缓存已配置完成，支持 Spring Cache 注解
   - 业务 Service 可直接使用 `@Cacheable` 和 `@CacheEvict` 注解
   - 无需额外的服务接口层

**使用示例**（在业务 Service 中直接使用）:

```java
// 从缓存获取知识库配置，TTL 10分钟
@Cacheable(value = "knowledge:config", key = "#id", unless = "#result == null")
public KnowledgeConfig getConfig(Long id) {
    // 第一次调用：缓存不存在 → 执行方法 → 方法返回后自动写入缓存 ✅
    // 后续调用：缓存存在 → 直接返回缓存值，不执行方法 ✅
    return knowledgeRepo.findConfigById(id);
}

// 更新时清除缓存
@CacheEvict(value = "knowledge:config", key = "#id")
public void updateConfig(Long id, KnowledgeConfig config) {
    // 方法执行完成后，自动清除缓存 ✅
    knowledgeRepo.updateConfig(id, config);
}
```

**缓存写入时机说明**:

- **@Cacheable**: 缓存是在**方法执行完成后**，**自动写入** Redis 的
  - 第一次调用：缓存不存在 → 执行方法 → **方法返回后自动写入缓存**
  - 后续调用：缓存存在 → 直接返回缓存值 → **不执行方法，不写入缓存**
- **@CacheEvict**: 缓存是在**方法执行完成后**，**自动清除**的
- **详细说明**: 请参考 `相关文档/Spring Cache 使用说明.md`

### 4.2 向量数据库选型分析

#### 4.2.1 pgvector vs 独立 Vector Database

##### pgvector（PostgreSQL 扩展）

**定义**: PostgreSQL 的扩展插件，在现有 PostgreSQL 数据库中支持向量类型和向量搜索

**特点**:

- ✅ **无需额外部署**: 使用现有 PostgreSQL，只需安装扩展
- ✅ **数据一致性**: 向量数据和业务数据在同一数据库中，事务一致
- ✅ **运维简单**: 只需维护一个数据库
- ✅ **成本低**: 无需额外的数据库服务
- ⚠️ **性能限制**: 大规模向量数据（> 1000 万）性能可能不如专业向量数据库
- ⚠️ **功能相对简单**: 缺少高级功能（如多模态、混合搜索等）

**适用场景**:

- 中小规模向量数据（< 1000 万向量）
- 需要与业务数据强一致性
- 希望简化运维和部署

##### 独立 Vector Database（Milvus、Qdrant、Chroma 等）

**定义**: 专门为向量搜索设计的数据库系统

**常见选择**:

- **Milvus**: 开源，功能强大，支持分布式
- **Qdrant**: 轻量级，性能优秀，Rust 编写
- **Chroma**: 简单易用，适合小规模场景
- **Weaviate**: 支持多模态，功能丰富

**特点**:

- ✅ **性能优秀**: 专为向量搜索优化，支持大规模数据
- ✅ **功能丰富**: 支持混合搜索、多模态、元数据过滤等
- ✅ **可扩展**: 支持分布式部署，水平扩展
- ❌ **额外部署**: 需要单独部署和维护
- ❌ **数据一致性**: 与业务数据分离，需要额外保证一致性
- ❌ **运维复杂**: 需要维护额外的数据库服务
- ❌ **成本高**: 需要额外的服务器资源

**适用场景**:

- 大规模向量数据（> 1000 万向量）
- 需要高性能向量搜索
- 需要高级功能（多模态、混合搜索等）

#### 4.2.2 项目选型建议

**推荐方案: pgvector**

**理由**:

1. **项目现状**: 已有 PostgreSQL，无需额外部署
2. **数据规模**: 知识库场景，向量数量通常在百万级别，pgvector 性能足够
3. **一致性要求**: 知识库数据需要与业务数据保持一致，pgvector 在同一事务中
4. **运维成本**: 无需维护额外的数据库服务
5. **开发成本**: 使用现有数据库，开发更简单

**不推荐独立 Vector Database 的原因**:

1. **过度设计**: 当前项目规模不需要独立的向量数据库
2. **运维复杂**: 增加系统复杂度
3. **数据一致性**: 需要额外保证向量数据库与 PostgreSQL 的一致性

**未来扩展**: 如果未来向量数据规模超过 1000 万，可以考虑迁移到 Milvus 或 Qdrant

#### 4.2.3 Apache Tika 说明

**Apache Tika 是什么**:

- Apache 基金会开发的文档内容提取和元数据检测工具
- 支持 1000+ 种文档格式（PDF、Word、Excel、PPT、TXT、HTML、图片等）
- 自动检测文档类型和编码
- 提取文档文本内容和元数据

**在项目中的作用**:

1. **文档解析**: 将各种格式的文档（PDF、Word、Excel 等）解析为纯文本
2. **格式统一**: 统一处理不同格式的文档，提取文本内容
3. **元数据提取**: 提取文档的元数据（作者、创建时间、标题等）

**使用示例**:

```java
@Service
public class DocumentParserService {

    private final Tika tika = new Tika();

    /**
     * 解析文档内容
     */
    public String parseDocument(MultipartFile file) {
        try {
            // 自动检测文档类型并解析
            String content = tika.parseToString(file.getInputStream());
            return content;
        } catch (Exception e) {
            throw new BusinessException(ResultCode.DOCUMENT_PARSE_FAILED,
                "文档解析失败: " + e.getMessage());
        }
    }

    /**
     * 提取文档元数据
     */
    public Metadata extractMetadata(MultipartFile file) {
        try {
            Metadata metadata = new Metadata();
            tika.parse(file.getInputStream(), metadata);
            return metadata;
        } catch (Exception e) {
            throw new BusinessException(ResultCode.DOCUMENT_PARSE_FAILED);
        }
    }
}
```

**支持的格式**:

- **文档**: PDF、Word (.doc, .docx)、Excel (.xls, .xlsx)、PowerPoint (.ppt, .pptx)
- **文本**: TXT、Markdown、HTML、XML、JSON
- **图片**: JPEG、PNG、GIF（需要 OCR 支持）
- **其他**: 压缩文件、邮件等

**注意事项**:

- 扫描 PDF（图片格式）需要 OCR 支持（可选，使用 Tesseract）
- 大文件解析可能较慢，建议异步处理
- 某些格式可能解析不完整，需要错误处理

### 4.4 核心功能实现方案

#### 4.4.1 知识库创建流程（LangChain）

```
1. 接收创建请求（provider=langchain）
   ↓
2. 创建知识库实体（保存到 PostgreSQL，provider='langchain'）
   ↓
3. 在 PostgreSQL 中创建对应的向量表（pgvector）
   - 表名: kb_vectors_{knowledge_id}
   - 字段: id, document_id, chunk_index, chunk_text, embedding, metadata
   ↓
4. 创建向量索引（ivfflat，加速搜索）
   ↓
5. 返回知识库信息
```

**技术要点**:

- 使用 `pgvector` 扩展在 PostgreSQL 中存储向量
- 每个知识库对应一个独立的向量表
- 向量表在知识库创建时自动创建

#### 4.4.2 文件上传与向量化流程（LangChain）

```
1. 接收文件上传请求（provider=langchain）
   ↓
2. 保存文件到 MinIO（复用现有 FileService）
   ↓
3. 解析文档内容（使用 Apache Tika）
   - 支持 PDF、Word、Excel、TXT 等格式
   - 提取纯文本和元数据
   ↓
4. 文本分块（Chunking）
   - 使用 LangChain4j 的 DocumentSplitter
   - 块大小: 1000 字符（可配置）
   - 重叠: 200 字符（可配置）
   ↓
5. 生成 Embedding（调用通义千问 Embedding API）
   - 批量处理，提高效率（每批 100 个块）
   - 维度: 1536（通义千问 text-embedding-v3）
   ↓
6. 存储向量到 PostgreSQL（pgvector）
   - 存储: 文档ID、块索引、块内容、向量、元数据
   - 使用事务保证一致性
   ↓
7. 更新知识库文件关联表（sys_knowledge_file_relation）
   ↓
8. 更新知识库文件计数
   ↓
9. 返回上传结果
```

**技术要点**:

- 文档解析: Apache Tika 统一处理各种格式
- 文本分块: 使用 LangChain4j 的 `DocumentSplitter`
- Embedding: 调用通义千问 Embedding API（支持批量）
- 向量存储: PostgreSQL + pgvector（使用 `vector` 类型）

#### 4.4.3 知识库对话流程（RAG，LangChain）

```
1. 接收对话请求（provider=langchain，knowledgeId 不为空）
   ↓
2. 将用户问题转换为 Embedding
   - 调用通义千问 Embedding API
   - 维度: 1536
   ↓
3. 向量相似度搜索（在知识库的向量表中）
   - 使用 pgvector 的余弦相似度搜索（<=> 操作符）
   - Top-K: 5（可配置）
   - 相似度阈值: 0.7（可配置）
   - SQL: SELECT ... WHERE 1 - (embedding <=> ?::vector) > ? ORDER BY embedding <=> ?::vector LIMIT ?
   ↓
4. 构建 Prompt（RAG）
   - 系统提示词: 定义 AI 角色和行为
   - 上下文: 将检索到的文档块作为上下文（最多 5 个块）
   - 用户问题: 用户的实际问题
   - 格式: "你是一个专业的AI助手。基于以下上下文回答问题：\n{context}\n\n问题：{question}"
   ↓
5. 调用 LLM 生成回答（流式）
   - 使用 LangChain4j 的 StreamingChatLanguageModel
   - 支持 SSE 流式返回
   ↓
6. 保存对话记录（可选）
   ↓
7. 流式返回给前端
```

**技术要点**:

- 向量搜索: 使用 PostgreSQL 的 `<=>` 操作符（余弦相似度）
- RAG 构建: 手动构建 Prompt，包含上下文和问题
- 流式响应: 使用 Spring WebFlux 的 `SseEmitter`

#### 4.4.4 纯对话流程（不使用知识库，LangChain）

```
1. 接收对话请求（provider=langchain，knowledgeId 为空）
   ↓
2. 直接调用 LLM（流式）
   - 使用 LangChain4j 的 StreamingChatLanguageModel
   - 支持 SSE 流式返回
   ↓
3. 流式返回给前端
```

```sql
CREATE TABLE kb_vectors_{knowledge_id} (
    id BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL COMMENT '文档ID（sys_knowledge_file_relation.id）',
    chunk_index INTEGER NOT NULL COMMENT '块索引（同一文档内的块序号）',
    chunk_text TEXT NOT NULL COMMENT '块文本内容',
    embedding vector(1536) NOT NULL COMMENT '向量（1536维，通义千问text-embedding-v3）',
    metadata JSONB COMMENT '元数据（文档名、文件类型等）',
    created_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (document_id) REFERENCES sys_knowledge_file_relation(id)
);

-- 创建向量索引（用于快速相似度搜索）
CREATE INDEX idx_kb_vectors_{knowledge_id}_embedding
ON kb_vectors_{knowledge_id}
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- 创建文档ID索引（用于删除文档时快速查找）
CREATE INDEX idx_kb_vectors_{knowledge_id}_document_id
ON kb_vectors_{knowledge_id}(document_id);
```

**注意**:

- `vector(1536)` 是通义千问 Embedding 的维度，如果使用其他模型需要调整
- `ivfflat` 索引用于加速向量搜索，`lists` 参数根据数据量调整（建议: 数据量/1000）
- 向量表在知识库创建时自动创建，在知识库删除时自动删除

```java
        String sql = String.format("""
            CREATE TABLE IF NOT EXISTS %s (
                id BIGSERIAL PRIMARY KEY,
                document_id BIGINT NOT NULL,
                chunk_index INTEGER NOT NULL,
                chunk_text TEXT NOT NULL,
                embedding vector(1536) NOT NULL,
                metadata JSONB,
                created_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
                FOREIGN KEY (document_id) REFERENCES sys_knowledge_file_relation(id)
            );

            CREATE INDEX IF NOT EXISTS idx_%s_embedding
            ON %s USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

            CREATE INDEX IF NOT EXISTS idx_%s_document_id
            ON %s(document_id);
            """, tableName, tableName, tableName, tableName, tableName);

        jdbcTemplate.execute(sql);
    }

    /**
     * 存储文档块向量
     */
    @Transactional(rollbackFor = Exception.class)
    public void storeVectors(Long knowledgeId, Long documentId,
                            List<TextSegment> segments) {
        String tableName = "kb_vectors_" + knowledgeId;

        // 批量生成 Embedding
        List<Embedding> embeddings = embeddingModel.embedAll(segments);

        // 批量插入向量
        String sql = String.format(
            "INSERT INTO %s (document_id, chunk_index, chunk_text, embedding, metadata) " +
            "VALUES (?, ?, ?, ?::vector, ?::jsonb)",
            tableName
        );

        for (int i = 0; i < segments.size(); i++) {
            TextSegment segment = segments.get(i);
            Embedding embedding = embeddings.get(i);

            jdbcTemplate.update(sql,
                documentId,
                i,
                segment.text(),
                embedding.contentAsString(),  // 转换为 PostgreSQL vector 格式
                buildMetadata(segment)
            );
        }
    }

    /**
     * 向量相似度搜索
     */
    public List<TextSegment> searchSimilar(Long knowledgeId,
                                          Embedding queryEmbedding,
                                          int topK,
                                          double similarityThreshold) {
        String tableName = "kb_vectors_" + knowledgeId;

        String sql = String.format(
            "SELECT chunk_text, metadata, 1 - (embedding <=> ?::vector) AS similarity " +
            "FROM %s " +
            "WHERE 1 - (embedding <=> ?::vector) > ? " +
            "ORDER BY embedding <=> ?::vector " +
            "LIMIT ?",
            tableName
        );

        return jdbcTemplate.query(sql,
            new Object[]{queryEmbedding.contentAsString(), similarityThreshold,
                        queryEmbedding.contentAsString(), topK},
            (rs, rowNum) -> {
                String chunkText = rs.getString("chunk_text");
                String metadata = rs.getString("metadata");
                double similarity = rs.getDouble("similarity");
                return TextSegment.from(chunkText, Metadata.from(metadata));
            }
        );
    }

    /**
     * 删除文档的所有向量
     */
    public void deleteVectorsByDocumentId(Long knowledgeId, Long documentId) {
        String tableName = "kb_vectors_" + knowledgeId;
        String sql = String.format("DELETE FROM %s WHERE document_id = ?", tableName);
        jdbcTemplate.update(sql, documentId);
    }

    /**
     * 删除知识库向量表
     */
    public void dropVectorTable(Long knowledgeId) {
        String tableName = "kb_vectors_" + knowledgeId;
        String sql = String.format("DROP TABLE IF EXISTS %s", tableName);
        jdbcTemplate.execute(sql);
    }

    private String buildMetadata(TextSegment segment) {
        // 构建元数据 JSON
        Map<String, Object> metadata = new HashMap<>();
        metadata.put("source", segment.metadata().get("source"));
        metadata.put("chunk_index", segment.metadata().get("chunk_index"));
        return new ObjectMapper().writeValueAsString(metadata);
    }
}
```

#### 4.6.4 RAG 实现（在 Service 层）

```java
@Service
@RequiredArgsConstructor
public class KnowledgeServiceImpl implements KnowledgeService {

    private final StreamingChatLanguageModel chatModel;
    private final PgVectorStoreService vectorStore;
    private final EmbeddingModel embeddingModel;
    private final DocumentParserService documentParser;
    private final TextSplitter textSplitter;

    @Override
    public SseEmitter chatbotStream(KnowledgeChatbotStreamReq req) {
        // 根据 provider 选择实现方式
        if ("langchain".equals(req.getProvider())) {
            return chatbotStreamLangChain(req);
        } else {
            return chatbotStreamDify(req);  // 现有 Dify 实现
        }
    }

    private SseEmitter chatbotStreamLangChain(KnowledgeChatbotStreamReq req) {
        SseEmitter emitter = new SseEmitter(60000L);

        globalTaskExecutor.execute(() -> {
            try {
                // 1. 生成问题 Embedding
                Embedding queryEmbedding = embeddingModel.embed(req.getQuery());

                // 2. 向量搜索
                List<TextSegment> relevantSegments = vectorStore.searchSimilar(
                    req.getKnowledgeId(),
                    queryEmbedding,
                    req.getTopK() != null ? req.getTopK() : 5,
                    req.getSimilarityThreshold() != null ? req.getSimilarityThreshold() : 0.7
                );

                // 3. 构建 Prompt
                String prompt = buildRAGPrompt(req.getQuery(), relevantSegments);

                // 4. 流式调用 LLM
                chatModel.generate(prompt, new StreamingResponseHandler<AiMessage>() {
                    @Override
                    public void onNext(String token) {
                        try {
                            emitter.send(SseEmitter.event()
                                .name("message")
                                .data(token));
                        } catch (Exception e) {
                            log.error("发送 SSE 数据失败", e);
                        }
                    }

                    @Override
                    public void onComplete(Response<AiMessage> response) {
                        try {
                            emitter.send(SseEmitter.event()
                                .name("message_end")
                                .data("{}"));
                            emitter.complete();
                        } catch (Exception e) {
                            log.error("完成 SSE 流失败", e);
                            emitter.completeWithError(e);
                        }
                    }

                    @Override
                    public void onError(Throwable error) {
                        log.error("LLM 流式生成失败", error);
                        emitter.completeWithError(error);
                    }
                });

            } catch (Exception e) {
                log.error("知识库对话失败", e);
                emitter.completeWithError(e);
            }
        });

        return emitter;
    }

    private String buildRAGPrompt(String query, List<TextSegment> segments) {
        StringBuilder context = new StringBuilder();
        for (TextSegment segment : segments) {
            context.append(segment.text()).append("\n\n");
        }

        return String.format("""
            你是一个专业的AI助手。基于以下上下文回答问题，如果上下文中没有相关信息，请说明无法从提供的上下文中找到答案。

            上下文：
            %s

            问题：%s

            请基于上下文回答问题：
            """, context.toString(), query);
    }
}
```

### 4.10 技术难点与解决方案

#### 4.10.1 难点 1: pgvector 集成

**问题**: PostgreSQL 需要安装 pgvector 扩展，且需要正确配置向量索引

**解决方案**:

- 在数据库初始化脚本中自动安装扩展
- 使用 `ivfflat` 索引加速向量搜索
- 提供索引参数调优指南（`lists` 参数根据数据量调整）

**潜在问题**:

- pgvector 扩展安装失败
- 向量索引创建失败
- 向量搜索性能问题

**应对措施**:

- 提供详细的安装文档和自动化脚本
- 索引创建失败时降级为全表扫描（性能下降但可用）
- 监控向量搜索性能，必要时优化索引参数

#### 4.10.2 难点 2: 文档解析

**问题**: 支持多种文档格式（PDF、Word、Excel 等）的解析

**解决方案**:

- 使用 Apache Tika 统一处理各种格式
- 对特殊格式（如扫描 PDF）提供 OCR 方案（可选）

**潜在问题**:

- 某些格式解析失败
- 大文件解析超时
- 扫描 PDF 无法解析文本

**应对措施**:

- 完善错误处理，解析失败时返回友好提示
- 大文件异步处理，提供进度查询
- 扫描 PDF 提示用户使用 OCR 或手动输入

#### 4.10.3 难点 3: 流式响应

**问题**: 实现真正的流式响应，实时返回 LLM 生成的内容

**解决方案**:

- 使用 LangChain4j 的 `StreamingChatLanguageModel`
- 通过 `StreamingResponseHandler` 实时处理 token
- 使用 Spring WebFlux 的 `SseEmitter` 推送给前端

**潜在问题**:

- SSE 连接断开
- 流式数据丢失
- 超时问题

**应对措施**:

- 实现心跳机制，保持连接活跃
- 错误重试机制
- 配置合理的超时时间

#### 4.10.4 难点 4: 向量搜索性能

**问题**: 大规模向量数据的搜索性能

**解决方案**:

- 使用 pgvector 的 `ivfflat` 索引
- 合理设置 `lists` 参数（根据数据量）
- 考虑分库分表（如果单个知识库向量数量 > 100 万）

**潜在问题**:

- 索引创建耗时
- 搜索性能下降
- 内存占用高

**应对措施**:

- 索引创建异步进行，不影响知识库创建
- 监控搜索性能，必要时优化索引参数
- 限制单个知识库的向量数量

#### 4.10.5 难点 5: 策略模式实现（Dify/LangChain 切换）

**问题**: 在现有 Service 中支持 Dify 和 LangChain 两种实现方式

**解决方案**:

- 使用策略模式，根据 `provider` 参数选择实现
- 复用现有实体和 DTO，通过字段区分
- 保持接口一致性

**潜在问题**:

- 代码复杂度增加
- 维护成本增加

**应对措施**:

- 清晰的代码结构，策略实现分离
- 完善的单元测试，确保两种实现都正确

### 4.11 优势与劣势分析

#### ✅ 优势

1. **完全自主可控**: 不依赖外部服务（Dify），所有逻辑自己控制
2. **灵活定制**: 可以根据业务需求灵活调整 RAG 策略
3. **成本可控**: 只需要支付 LLM 和 Embedding API 费用，无平台费用
4. **数据安全**: 向量数据存储在自有数据库中，数据不外泄
5. **性能优化**: 可以根据实际情况优化向量搜索和文档处理性能
6. **架构一致**: 严格遵循 DDD 分层架构，不破坏现有设计
7. **平滑切换**: 与现有 Dify 方案并行，前端可通过参数切换

#### ⚠️ 劣势

1. **开发工作量大**: 需要实现文档解析、向量化、RAG 等完整流程
2. **维护成本高**: 需要维护向量数据库、索引、文档处理等基础设施
3. **功能相对简单**: 相比 Dify，缺少工作流编排、多模态等高级功能
4. **技术门槛**: 需要深入理解 RAG、向量搜索等技术
5. **代码复杂度**: 需要同时维护 Dify 和 LangChain 两套实现
